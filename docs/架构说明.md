# 架构说明

## 1. 项目目标

`lightweight-ip-traffic-sa` 是一个面向 IP 安全态势感知场景的前后端分离项目，当前优先做实以下主链路：

1. 登录鉴权
2. 安全任务创建与查询
3. 特征采集与风险评分
4. 总览展示
5. 预警中心
6. 历史记录
7. 安全配置维护

当前阶段重点不是重构底层框架，而是在现有骨架上持续补强业务可用性、文档可交接性和验证闭环。

## 2. 技术架构

### 2.1 后端

- 语言：Go `1.24.x`
- Web 框架：Gin
- ORM：Gorm
- 数据库：MySQL
- 缓存：Redis
- 认证：JWT
- 配置：YAML

### 2.2 前端

- 框架：Vue 3
- 构建：Vite
- 路由：Vue Router
- 状态管理：Pinia
- HTTP：Axios
- UI：Element Plus
- 图表：ECharts、vue-echarts

## 3. 目录与职责

### 3.1 后端目录

- `server/main.go`
  - 启动入口
- `server/initialize`
  - 配置、Redis、数据库、路由、演示数据初始化
- `server/router`
  - 路由分组与 URL 组织
- `server/api/v1`
  - 控制器层，负责参数绑定与统一响应
- `server/service`
  - 业务编排与规则处理
- `server/repository`
  - 数据访问封装
- `server/model`
  - 实体、请求模型、响应模型
- `server/middleware`
  - JWT 与角色校验

### 3.2 前端目录

- `web/src/router`
  - 路由入口与模块路由
- `web/src/api`
  - Axios 封装与业务 API
- `web/src/pinia`
  - 登录态与用户信息状态
- `web/src/view`
  - 页面视图
- `web/src/components/security`
  - 安全域复用组件

## 4. 启动链路

当前后端运行时启动顺序如下：

1. `server/main.go` 调用 `initialize.Run()`
2. 从 `server/config.yaml` 读取配置
3. 初始化 Redis，失败时自动降级为无缓存模式
4. 初始化 MySQL 并执行缺失表自动迁移
5. 自动补齐默认演示用户与默认安全配置
6. 创建 Gin 引擎并注册 `/api/v1` 路由
7. 启动 HTTP 服务

这个流程说明当前项目已经内置“最小可运行环境”的初始化闭环，不依赖完全手工导库后才能启动。

## 5. 后端分层设计

### 5.1 路由层

路由层只负责 URL 分组和中间件挂载。

当前核心分组：

- `system`
  - 登录、登出、当前用户、用户管理
- `security`
  - 任务、总览、预警、记录、配置

### 5.2 API 层

API 层负责：

1. 接收参数
2. 调用服务
3. 返回统一结构
4. 将校验失败映射为明确 HTTP 状态码与消息

不应把复杂采集流程、缓存策略或多仓储编排写在此层。

### 5.3 Service 层

Service 层负责：

1. 安全任务编排
2. 画像、特征、评分、预警联动
3. 总览聚合
4. 历史记录整合
5. 安全配置读写与运行时同步
6. 缓存读写与失效控制

### 5.4 Repository 层

Repository 层负责：

1. 查询条件拼装
2. 列表与分页数据访问
3. 领域对象持久化

当前项目已经把多数数据访问下沉到 `repository`，有利于后续继续梳理服务边界。

## 6. 路由与权限模型

### 6.1 后端路由装配

后端所有接口统一挂在 `/api/v1` 下。

路由分为两类：

1. 公共路由
   - `POST /api/v1/system/login`
2. 私有路由
   - 所有其余 `system` 和 `security` 接口
   - 统一挂载 JWT 鉴权中间件

部分接口再叠加角色限制：

- `ADMIN`
  - 用户管理相关接口
- `ADMIN`、`MANAGER`
  - 创建任务
  - 更新安全配置

### 6.2 前端路由装配

前端核心页面路由如下：

- `/login`
- `/security/overview`
- `/security/task`
- `/security/task/:id`
- `/security/history`
- `/security/alert`
- `/security/alert/:id`
- `/security/config`
- `/system/users`

前端在 `router.beforeEach` 中做以下控制：

1. 判断是否需要登录
2. 若已持有 token，则补拉当前用户信息
3. 按 `meta.roles` 判断页面访问权限
4. 401 时清理 token 并跳转登录页

## 7. 当前业务主链路

### 7.1 登录链路

1. 登录页调用 `web/src/api/user.js`
2. 后端返回 token 与用户信息
3. Pinia 持久化 token
4. Axios 请求拦截器注入 `Authorization: Bearer <token>`
5. 路由守卫按登录态和角色控制页面访问

### 7.2 安全任务链路

1. 前端任务页提交目标 IP
2. 后端创建任务记录
3. 服务层执行采集、基础信息、特征、评分、预警流水线
4. 结果写入多张安全域表
5. 返回任务创建结果并清理总览缓存

### 7.3 总览链路

1. 总览页获取 `/dashboard/summary`
2. 同时拉取任务列表与预警列表生成图表数据
3. 当 Redis 可用时，总览聚合结果走短 TTL 缓存

### 7.4 历史链路

历史页不是单独一张表的直出，而是由服务层把任务记录与预警记录合并后统一分页返回。

### 7.5 配置链路

1. 页面读取 `/configs/security`
2. 服务层优先从缓存读取
3. 修改配置后写回数据库
4. 同步更新运行时内存配置并刷新缓存

## 8. 缓存与降级

当前已确认的缓存点：

1. `GET /api/v1/dashboard/summary`
   - 键：`utils.SecurityDashboardSummaryCacheKey`
   - TTL：`30s`
   - 任务创建成功后会主动清理
2. `GET /api/v1/configs/security`
   - 键：`utils.SecurityConfigCacheKey`
   - TTL：`5m`
   - 配置更新后会主动回写缓存

降级策略：

1. Redis 关闭时直接跳过缓存
2. Redis 初始化失败时打印日志并继续启动
3. 缓存读写失败不会阻断主业务逻辑

## 9. 页面状态覆盖现状

从当前前端实现看，安全域页面已具备以下基础能力：

1. `loading` 状态
2. 请求失败提示
3. 列表空态或图表空态
4. 基于角色的只读提示或页面访问限制

仍需在真实运行环境中继续完成浏览器级逐页验证，重点关注：

1. 401 失效跳转
2. 403 权限提示
3. 详情页数据为空时的表现
4. 配置页与用户管理页的角色边界

## 10. 当前架构结论

截至 `2026-04-06`，项目架构已经具备以下特点：

1. `system + security` 双域结构稳定
2. 前后端主链路已连通到可继续联调的程度
3. 缓存接入已形成明确边界与降级逻辑
4. 文档、运行说明、接口约定已开始与真实实现对齐

下一阶段的重点不再是补框架，而是继续做细真实联调、包体优化与残余页面状态验证。
# 2026-04-20 架构补充

- 新的实时流量监控链路为独立会话链路：`/security/monitor -> /api/v1/flow-monitor/sessions -> 会话状态存储 -> Npcap + gopacket 5 秒循环采样 -> 阈值判定 -> 预警中心`
- 该链路不再依赖任务创建流程，不再绑定任务 ID，也不进入检测历史与任务流量三表

- 默认业务主链、任务详情页流量承接链、实时监控独立链三者当前已分离；实时监控属于“独立网卡监听能力”，不等同于任务流量承接
