# 03. 核心任务链路：从创建到评分预警

## 一、本章要解决的问题

用户在前端输入 `8.8.8.8`，点击"开始检测"，后端发生了什么？为什么接口秒回，但详情页要等几秒才能看到评分？

## 二、整体流程图

```
前端                   后端                         数据库
 |                     |                            |
 |-- POST /tasks ----->|                            |
 |                     |-- 1.校验 IP/域名           |
 |                     |-- 2.写任务表(PENDING) ---->|
 |                     |-- 3.更新状态(RUNNING) ---->|
 |                     |-- 4.清理总览缓存          |
 |                     |-- 5.启动 goroutine 异步采集
 |<-- 返回 taskID -----|                            |
 |                     |                            |
 |                     |  [异步 goroutine]          |
 |                     |-- 6.采集四维数据          |
 |                     |-- 7.归一化+加权评分        |
 |                     |-- 8.事务写入多表 --------->|
 |                     |-- 9.更新状态(SUCCESS) ---->|
 |                     |-- 10.写审计日志 ---------->|
 |                     |                            |
 |-- GET /tasks/:id -->|                            |
 |                     |-- 查询任务+画像+评分+预警  |
 |<-- 返回完整详情 -----|                            |
```

## 三、代码走读：CreateTask

文件：`server/service/security/task_service.go`

### 第 1 步：校验输入

```go
func (s *TaskService) CreateTaskWithActor(req requestModel.CreateTaskRequest, actor string) (responseModel.TaskCreateResponse, error) {
    // 1. 校验目标 IP 或域名
    resolvedTarget, err := validateCreateTaskRequest(req)
    if err != nil {
        return responseModel.TaskCreateResponse{}, err
    }
    // resolvedTarget 结构：
    // {
    //   InputType:  "IP" 或 "DOMAIN",
    //   InputValue: "8.8.8.8" 或 "google.com",
    //   TargetIP:   "8.8.8.8"  // 如果是域名，解析成 IP
    // }
}
```

`validateCreateTaskRequest` 做的事：
- 如果是 IP：直接返回
- 如果是域名：调用 DNS 解析成 IP
- 如果都不是：返回错误

### 第 2 步：写任务表（PENDING）

```go
task := securityModel.IPTask{
    TaskNo:      buildTaskNo(time.Now()),  // 生成任务编号：TASK-20260420143025-123456789-1234-1
    InputType:   resolvedTarget.InputType,
    InputValue:  resolvedTarget.InputValue,
    TargetIP:    resolvedTarget.TargetIP,
    CreatedBy:   actor,
    TaskStatus:  "PENDING",               // ← 初始状态
    CreatedAt:   time.Now(),
}
repo.TaskRepository.Create(global.DB, &task)
```

### 第 3 步：更新为 RUNNING

```go
repo.TaskRepository.UpdateStatus(global.DB, task.ID, map[string]interface{}{
    "task_status": "RUNNING",
    "started_at":  &startedAt,
})
task.TaskStatus = "RUNNING"
```

**为什么要先 PENDING 再 RUNNING？**
- PENDING 表示"任务已创建，但还没开始执行"
- RUNNING 表示"任务正在执行"
- 如果创建后直接更新为 RUNNING 失败，可以用 PENDING 状态做重试

### 第 4 步：清理总览缓存

```go
_ = utils.CacheDelete(utils.SecurityDashboardSummaryCacheKey)
```

**为什么？** 总览页会统计"今日检测数"、"风险分布"，新任务创建后，这些统计应该立即更新，不能让用户看到旧缓存。

### 第 5 步：启动异步 goroutine

```go
go taskPipelineAsyncExecutor(securityTaskExecutionContext{
    TaskID:   task.ID,
    TaskNo:   task.TaskNo,
    TargetIP: task.TargetIP,
    Actor:    createdBy,
})
```

**关键**：`go` 关键字启动一个 goroutine（Go 的轻量级线程），异步执行采集和评分。

**接口立即返回**：

```go
return responseModel.TaskCreateResponse{
    TaskID:     task.ID,
    TaskNo:     task.TaskNo,
    TargetIP:   task.TargetIP,
    TaskStatus: "RUNNING",
    ScoreValue: 0,          // ← 还没评分，所以是 0
    RiskLevel:  "",
    AlertCreated: false,
}, nil
```

前端拿到 `taskID` 后，可以：
- 跳转到任务详情页
- 轮询 `/tasks/:id` 接口，直到 `taskStatus` 变成 `SUCCESS`

## 四、代码走读：runTaskPipeline（异步执行）

这是真正的"干活"部分。

### 第 6 步：采集四维数据

```go
func (s *TaskService) runTaskPipeline(task securityTaskExecutionContext) {
    // 加载运行时配置（阈值、权重、数据源开关）
    runtimeConfig := loadRuntimeSecurityConfig()

    // 构建采集流水线
    pipeline := NewTaskPipelineBuilder(runtimeConfig)

    // 执行采集 + 评分 + 预警
    pipelineResult, err := pipeline.Build(task.TaskID, task.TaskNo, task.TargetIP, runtimeConfig)
}
```

`pipeline.Build()` 内部做的事（在 `pipeline_components.go`）：
1. 调用 `BaseInfoCollector.Collect()` → 基础画像（国家、ISP、ASN）
2. 调用 `ReputationCollector.Collect()` → 信誉风险分
3. 调用 `AttackSurfaceCollector.Collect()` → 攻击面（开放端口数、高危端口数）
4. 调用 `FlowCollector.Collect()` → 流量行为分
5. 调用 `FeatureNormalizer.Normalize()` → 归一化成四个风险分
6. 调用 `ScoreCalculator.Calculate()` → 加权评分 + 规则修正
7. 调用 `AlertDecider.Decide()` → 判断是否触发预警

### 第 7 步：事务写入多表

```go
err = global.DB.Transaction(func(tx *gorm.DB) error {
    // 1. 写基础画像表
    repo.BaseInfoRepository.Create(tx, &pipelineResult.BaseInfo)

    // 2. 写特征快照表
    repo.FeatureRepository.Create(tx, &pipelineResult.FeatureSnapshot)

    // 3. 写风险评分表
    repo.ScoreRepository.Create(tx, &pipelineResult.RiskScore)

    // 4. 如果触发预警，写预警表
    if pipelineResult.AlertRecord != nil {
        pipelineResult.AlertRecord.ScoreID = &pipelineResult.RiskScore.ID
        repo.AlertRepository.Create(tx, pipelineResult.AlertRecord)
    }

    // 5. 如果有流量数据，写流量三表
    if pipelineResult.FlowCollection != nil {
        repo.FlowCollectionRepository.Create(tx, pipelineResult.FlowCollection)
        repo.FlowWindowAggregateRepository.CreateInBatches(tx, pipelineResult.FlowWindows, 200)
        repo.FlowFeatureSnapshotRepository.Create(tx, pipelineResult.FlowFeature)
    }

    // 6. 更新任务状态为 SUCCESS
    repo.TaskRepository.UpdateStatus(tx, task.TaskID, map[string]interface{}{
        "task_status": "SUCCESS",
        "finished_at": &finishedAt,
    })

    return nil
})
```

**为什么要用事务？**

如果不用事务，可能出现这种情况：
- 基础画像写入成功
- 评分写入成功
- 预警写入失败

结果：任务显示"成功"，但用户看不到预警，数据不一致。

用事务后：要么全成功，要么全失败回滚，任务标记为 FAILED。

### 第 8 步：失败处理

```go
if err != nil {
    // 事务失败，标记任务为 FAILED
    s.markTaskFailed(task.TaskID, err.Error())
    log.Printf("async task persistence failed, taskID=%d err=%v", task.TaskID, err)
    return
}
```

## 五、任务状态机

任务有以下状态：

```
PENDING  →  RUNNING  →  SUCCESS
              ↓
           FAILED
```

代码里还有删除操作，但删除是直接 DELETE SQL，不是状态变更。

**状态存储位置**：`sec_ip_task` 表的 `task_status` 字段。

## 六、任务详情查询

文件：`server/service/security/task_service.go` 的 `GetTaskDetail()`

这个方法做的事：
1. 先查缓存：`utils.CacheGetJSON(BuildTaskDetailCacheKey(taskID), &cached)`
2. 缓存没命中，查数据库：
   - 查任务主表 `sec_ip_task`
   - 查基础画像 `sec_ip_base_info`
   - 查特征快照 `sec_feature_snapshot`
   - 查评分 `sec_risk_score`
   - 查预警 `sec_alert_record`
   - 查流量三表
3. 组装成 `TaskDetailResponse` 返回
4. 写入缓存：`utils.CacheSetJSON(cacheKey, resp, DetailQueryCacheTTL())`

**为什么任务详情要缓存？**
- 详情页可能被打开放大镜反复看
- 任务完成后数据不会再变，适合缓存
- TTL 设 120 秒，平衡实时性和性能

## 七、删除任务的级联清理

```go
func (s *TaskService) DeleteTask(taskID uint64) error {
    err = global.DB.Transaction(func(tx *gorm.DB) error {
        // 按顺序删除关联表
        repo.AlertRepository.DeleteByTaskID(tx, taskID)
        repo.FlowFeatureSnapshotRepository.DeleteByTaskID(tx, taskID)
        repo.FlowWindowAggregateRepository.DeleteByTaskID(tx, taskID)
        repo.FlowCollectionRepository.DeleteByTaskID(tx, taskID)
        repo.ScoreRepository.DeleteByTaskID(tx, taskID)
        repo.FeatureRepository.DeleteByTaskID(tx, taskID)
        repo.BaseInfoRepository.DeleteByTaskID(tx, taskID)
        repo.TaskRepository.DeleteByID(tx, taskID)  // 最后删主表
        return nil
    })

    // 清理缓存
    utils.CacheDelete(BuildTaskDetailCacheKey(taskID), SecurityDashboardSummaryCacheKey)
}
```

**为什么要手动删除关联表？**

虽然数据库定义了外键，但没加 `ON DELETE CASCADE`。为什么？
- 显式删除更可控，可以在删除前做检查（比如"这个任务有关联预警，确定要删吗？"）
- 避免级联删除误删数据

## 八、关键设计点总结

### 1. 为什么异步？

如果同步执行：
- 用户点"开始检测"，接口要卡 5~10 秒才返回
- 前端体验差，以为系统卡死
- 如果采集超时，HTTP 请求也超时

异步后：
- 接口秒回 taskID
- 前端轮询或 WebSocket 获取结果
- 采集超时不影响接口响应

### 2. 为什么用 goroutine 不用消息队列？

goroutine 简单，不用引入额外组件。但缺点：
- 进程重启，正在执行的任务会丢失
- 无法做任务队列管理（暂停、优先级、限流）

**生产环境改进**：用 Asynq（基于 Redis 的任务队列）或 RabbitMQ。

### 3. 为什么用事务？

任务结果涉及 7 张表，任何一张写失败都会导致数据不一致。事务保证"要么全成功，要么全失败"。

### 4. 为什么清理缓存时机不同？

- 创建任务时清理：让总览统计立即反映新任务
- 任务完成时清理：让总览统计更新评分结果
- 删除任务时清理：避免缓存里有已删除任务的幽灵数据

## 九、本章 Q&A

**Q：如果用户连续创建 100 个任务，goroutine 会不会爆？**
A：会。goroutine 虽然轻量，但 100 个并发采集会同时访问 GeoLite2、RDAP、端口探测，可能把外部服务打挂。

改进方案：
1. 用 `semaphore` 限制并发数（比如最多 10 个并发任务）
2. 用任务队列，按顺序执行
3. 加限流中间件，限制用户创建任务的频率

**Q：任务执行到一半，进程重启了怎么办？**
A：当前实现：任务会永远卡在 RUNNING 状态。

改进方案：
1. 启动时扫描所有 RUNNING 状态任务，重新执行或标记为 FAILED
2. 用心跳机制：goroutine 定期更新任务的 `updated_at`，如果超过 5 分钟没更新，认为任务僵死，重新调度

**Q：为什么任务详情要组装这么多表？不能合成一张大宽表吗？**
A：可以，但有缺点：
1. 大宽表字段太多（画像 + 特征 + 评分 + 预警 + 流量，几十列），查询和维护都麻烦
2. 不是所有任务都有流量数据，大宽表会有很多 NULL 字段
3. 分表符合第三范式，更新某一部分时不影响其他

缺点：
1. 查询要 JOIN 多表，性能差一点
2. 代码复杂（要组装多个 model）

本项目数据量小，分表更合适。

**Q：如果采集过程中 RDAP 超时了，整个任务会失败吗？**
A：不会。RDAP 是增强数据源，超时会记录降级原因，继续用 GeoLite2 的数据。只有**所有数据源都失败**或**参数本身错误**时，任务才会 FAILED。

这体现了"增强能力可降级"的设计思想。

**Q：为什么任务编号要包含时间戳 + 纳秒 + 进程ID + 原子计数器？**

```go
func buildTaskNo(now time.Time) string {
    return fmt.Sprintf("TASK-%s-%09d-%d-%d",
        now.Format("20060102150405"),  // 时间戳
        now.Nanosecond(),               // 纳秒
        os.Getpid(),                    // 进程 ID
        taskNoSequence.Add(1))          // 原子计数器
}
```

A：为了全局唯一，防止：
- 同一秒创建多个任务 → 纳秒区分
- 多实例部署 → 进程 ID 区分
- 同一进程并发 → 原子计数器区分
