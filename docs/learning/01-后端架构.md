# 01. 后端架构：分层 + 启动链路

## 一、为什么要分层？

不分层的代码长这样：路由里直接写 SQL、HTML 拼接、业务规则混在一起，100 行后就读不懂了。

分层的核心是**单一职责**：每层只做一件事，改一层不影响其他层。

## 二、五层架构总览

```
HTTP 请求
   ↓
[router]      路由层     → 只负责 URL 分组和挂中间件
   ↓
[api/v1]      控制器层   → 参数绑定 + 参数校验 + 调用 service + 统一响应
   ↓
[service]     业务层     → 业务编排、规则计算、调用多个 repository
   ↓
[repository]  仓储层     → SQL/ORM 调用，返回领域对象
   ↓
[model]       模型层     → 结构体定义：数据库实体 / 请求 / 响应
   ↓
MySQL / Redis / 文件 / 外部 API
```

对应目录：

```
server/
├── router/        # router/security/task.go、router/system/auth.go
├── api/v1/        # api/v1/security/task.go
├── service/       # service/security/task_service.go
├── repository/    # repository/security/task_repository.go
└── model/         # model/security/ip_task.go
```

## 三、每层职责 + 项目里的例子

### 1. router 层：只负责 URL → 处理函数的映射

```go
// server/router/security/task.go 节选
func InitTaskRouter(Router *gin.RouterGroup) {
    taskRouter := Router.Group("tasks")
    {
        taskRouter.POST("", taskApi.CreateTask)            // POST   /api/v1/tasks
        taskRouter.GET("", taskApi.ListTasks)              // GET    /api/v1/tasks
        taskRouter.GET(":id", taskApi.GetTaskDetail)       // GET    /api/v1/tasks/:id
        taskRouter.DELETE(":id", taskApi.DeleteTask)       // DELETE /api/v1/tasks/:id
    }
}
```

**这一层不写业务**。看到路由就知道 URL 长什么样。

### 2. api 层：参数绑定 + 调用 service + 统一响应

```go
// 伪代码示意（实际在 server/api/v1/security/task.go）
func (api *TaskApi) CreateTask(c *gin.Context) {
    var req requestModel.CreateTaskRequest
    if err := c.ShouldBindJSON(&req); err != nil {
        c.JSON(400, response.Fail("参数错误"))
        return
    }
    resp, err := taskService.CreateTask(req)
    if err != nil {
        c.JSON(500, response.Fail(err.Error()))
        return
    }
    c.JSON(200, response.Ok(resp))
}
```

**职责**：HTTP 世界 ↔ 业务世界的翻译。把 JSON 解析成结构体，把业务错误翻译成 HTTP 状态码。

### 3. service 层：业务编排

这是项目的"心脏"。例如 `task_service.go` 的 `CreateTask`：
1. 校验 IP/域名
2. 写任务表（PENDING → RUNNING）
3. 启动 goroutine 异步跑采集+评分
4. 清理总览缓存
5. 返回 taskID 给前端

### 4. repository 层：只跟数据库打交道

```go
// server/repository/security/task_repository.go 伪代码示意
func (r *TaskRepository) Create(db *gorm.DB, task *model.IPTask) error {
    return db.Create(task).Error
}

func (r *TaskRepository) UpdateStatus(db *gorm.DB, id uint64, updates map[string]interface{}) error {
    return db.Model(&model.IPTask{}).Where("id = ?", id).Updates(updates).Error
}
```

**好处**：换 ORM、改 SQL、加缓存，只动这一层。

### 5. model 层：结构体定义

```go
// server/model/security/ip_task.go
type IPTask struct {
    ID          uint64     `gorm:"primaryKey"`
    TaskNo      string     `gorm:"column:task_no"`
    TargetIP    string     `gorm:"column:target_ip"`
    TaskStatus  string     `gorm:"column:task_status"`
    // ...
}
```

分三种：
- **实体**（Entity）：跟数据库表一一对应
- **请求**（Request）：`model/security/request/`，HTTP 入参
- **响应**（Response）：`model/security/response/`，HTTP 出参

## 四、启动链路（main.go → 服务就绪）

读 `server/main.go`（只有 15 行）：

```go
package main

import (
    "log"
    "lightweight-ip-traffic-sa/server/initialize"
)

func main() {
    if err := initialize.Run(); err != nil {
        log.Fatal(err)
    }
}
```

`initialize.Run()` 在 `server/initialize/server.go`，按顺序做 5 件事：

```
1. LoadConfig()                读 config.yaml → 全局变量 global.AppConfig
2. InitRedis()                 失败时打印日志，但**不退出**（降级为无缓存模式）
3. InitDB()                    失败时**直接退出**（MySQL 是硬依赖）
4. InitDemoUsers()             自动补种子数据：admin 账号、默认安全配置
5. SetupRouter().Run(":8080")  启动 Gin HTTP 服务
```

**面试要点**：
- 为什么 Redis 失败可以降级，MySQL 失败必须退出？
  → Redis 只是缓存，挂了可以查 MySQL。MySQL 是主存储，挂了所有业务都没法跑。
- 为什么要做种子数据？
  → 让项目"开箱即用"，新人 clone 下来不用手工建账号就能登录。

## 五、双域划分：system + security

后端按业务域拆成两块：

```
server/
├── router/system/       # 登录、用户、审计
├── router/security/     # 任务、预警、配置、流量监控
├── api/v1/system/
├── api/v1/security/
├── service/system/
├── service/security/
├── repository/system/
├── repository/security/
├── model/system/
└── model/security/
```

**好处**：
1. **职责清晰**：`system` 管"人"，`security` 管"事"
2. **可独立演进**：未来想把 `security` 拆成微服务，目录已经分好了
3. **权限边界清楚**：`system` 接口只有 ADMIN，安全业务接口 ADMIN/MANAGER/USER 都能访问

## 六、URL 设计

所有业务接口都在 `/api/v1` 前缀下：

```
POST   /api/v1/system/login                 # 登录（公共，不需要 token）
POST   /api/v1/system/logout                # 登出
GET    /api/v1/system/current-user          # 当前用户
GET    /api/v1/system/users                 # 用户列表（仅 ADMIN）
GET    /api/v1/system/audit-logs            # 审计日志（仅 ADMIN）

POST   /api/v1/tasks                        # 创建任务（ADMIN/MANAGER）
GET    /api/v1/tasks                        # 任务列表
GET    /api/v1/tasks/:id                    # 任务详情
DELETE /api/v1/tasks/:id                    # 删除任务
GET    /api/v1/dashboard/summary            # 总览
GET    /api/v1/records                      # 历史记录
GET    /api/v1/alerts                       # 预警列表
GET    /api/v1/alerts/:id                   # 预警详情
GET    /api/v1/configs/security             # 读配置（ADMIN/MANAGER）
PUT    /api/v1/configs/security             # 改配置（ADMIN/MANAGER）
POST   /api/v1/flow-monitor/sessions        # 启动实时监控
```

**设计要点**：
- 用名词复数 `/tasks` 而不是 `/getTask`（RESTful 风格）
- 用 HTTP 方法区分动作：GET 查询、POST 创建、PUT 修改、DELETE 删除
- 用路径层级表达归属：`/tasks/:id` 是某个具体任务

## 七、中间件执行顺序

Gin 的中间件是洋葱模型，请求像穿过一层层洋葱：

```
请求
  → [CORS 中间件]
  → [JWTAuth 中间件]      ← 解析 token，黑名单检查
  → [RequireRoles 中间件] ← 检查角色
  → [API 处理函数]
  → [service]
  → ...
响应
```

代码位置：`server/middleware/jwt.go` 的 `JWTAuth()` 和 `RequireRoles()`。

挂载位置：`server/router/security/group.go` 和 `server/router/system/group.go`，把这两组路由挂上 JWT 中间件。

## 八、错误处理约定

项目用 `ServiceError` 包装业务错误，分类成：
- `InvalidArgument` → 400
- `NotFound` → 404
- `ExternalDependency` → 503
- `Internal` → 500

API 层根据错误类别返回对应 HTTP 状态码。

**为什么不用 panic？** panic 会让整个进程崩溃。业务错误应该作为正常流程的一部分被处理掉。

## 九、配置管理

两层配置：
1. **启动配置** `server/config.yaml`：端口、DB DSN、Redis 地址、默认权重、默认阈值
2. **运行时配置** 表 `sec_security_config`：流量模式、阈值、权重、数据源开关

优先级：运行时配置 > 启动配置。代码在 `loadRuntimeSecurityConfig()`（`server/service/security/pipeline_components.go`）。

**好处**：改阈值不用重启服务，前端配置页直接改。

## 十、本章 Q&A

**Q：为什么用 Gin 不用 Echo / Beego？**
A：Gin 是 Go 生态里使用最广的 HTTP 框架，文档全、社区活跃、性能足够。对这个项目来说，框架不是关键瓶颈，生态和开发效率更重要。

**Q：为什么用 Gorm 不用原生 SQL？**
A：Gorm 把 CRUD 写得很快，事务、关联查询、迁移都有现成方法。缺点是会隐藏 SQL，对性能敏感的场景需要看生成的 SQL。本项目是 CRUD 密集型，Gorm 合适。

**Q：Service 层和 Repository 层为什么要分开？合并成一层不行吗？**
A：能合，但分开有两个好处：
1. Service 写业务逻辑时不用关心 SQL，看 Repository 方法名就知道在干什么
2. 单元测试时可以 mock Repository，让 Service 测试不依赖真实数据库

**Q：双域 system + security 和微服务有什么区别？**
A：微服务是**进程级**拆分（不同服务部署在不同机器），双域是**代码级**拆分（同一个进程、同一个数据库，但目录分开）。本项目是双域单体的"模块化单体"（Modular Monolith），未来要拆微服务比较容易。

**Q：如果让你重新设计，会改哪里？**
A：
- 把任务异步执行改成消息队列（如 Asynq / RabbitMQ），目前用 goroutine 在进程内异步，重启会丢任务
- 加 Prometheus 指标暴露
- 加分布式链路追踪（OpenTelemetry）
