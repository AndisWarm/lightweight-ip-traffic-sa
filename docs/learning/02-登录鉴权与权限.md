## 一、本章要解决的问题

1. 用户登录后，后端怎么知道"这是谁"？
2. 用户退出后，怎么让 token 立即失效？

## 二、JWT 是什么？

JWT（JSON Web Token）是一段加密的字符串，长这样：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VybmFtZSI6ImFkbWluIiwicm9sZSI6IkFETUlOIiwiZXhwIjoxNzI5MjgwMDAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

它由三部分组成，用 `.` 分隔：
- **Header**（头部）：算法和类型
- **Payload**（载荷）：用户数据（username、role、过期时间）
- **Signature**（签名）：用密钥对前两部分签名，防止篡改

**关键特性**：
- ✅ 无状态：服务端不用存 session，token 自包含用户信息
- ✅ 可跨域：前端可以把它放在 HTTP Header 里发给任意后端
- ❌ 一旦签发，在过期前都有效（除非加黑名单）

## 三、JWT 在项目里的完整流程

### 1. 登录时签发 token

```go
// server/service/system/auth_service.go 伪代码
func (s *AuthService) Login(username, password string) (token string, user User, err error) {
    // 1. 查数据库验证用户名密码
    user := userRepo.FindByUsername(username)
    if !user.CheckPassword(password) {
        return "", User{}, errors.New("密码错误")
    }

    // 2. 生成 JWT
    claims := TokenClaims{
        Username: user.Username,
        RoleCode: user.RoleCode,
        ExpiresAt: time.Now().Add(24 * time.Hour),
    }
    token = utils.GenerateToken(claims)
    return token, user, nil
}
```

### 2. 前端存 token

```javascript
// web/src/pinia/modules/user.js
const useUserStore = defineStore('user', {
    state: () => ({
        token: '',
        userInfo: {},
    }),
    actions: {
        async login(loginForm) {
            const res = await loginApi(loginForm)
            this.token = res.data.token
            this.userInfo = res.data.userInfo
            localStorage.setItem('token', res.data.token)
        },
    },
})
```

### 3. 每次请求带 token

```javascript
// web/src/api/request.js
axios.interceptors.request.use(config => {
    const token = localStorage.getItem('token')
    if (token) {
        config.headers.Authorization = `Bearer ${token}`
    }
    return config
})
```

### 4. 后端中间件验证 token

```go
// server/middleware/jwt.go
func JWTAuth() gin.HandlerFunc {
    return func(c *gin.Context) {
        token := utils.ExtractToken(c)              // 从 Header 取 token
        claims, err := utils.ParseToken(token)      // 解析 token
        if err != nil {
            c.JSON(401, response.Fail("未登录或登录状态已失效"))
            c.Abort()                               // 阻止继续执行
            return
        }

        // 检查黑名单（关键！）
        blacklisted, _ := authService.IsTokenBlacklisted(token)
        if blacklisted {
            c.JSON(401, response.Fail("登录状态已失效"))
            c.Abort()
            return
        }

        c.Set("claims", claims)                     // 把用户信息存到上下文
        c.Next()                                    // 继续执行下一个中间件/处理函数
    }
}
```

## 四、JWT 黑名单：解决"退出后 token 仍有效"

### 问题

JWT 是无状态的：签发后在过期前都有效。如果用户点了"退出登录"，前端删除了 token，但这个 token 如果被别人复制了，还能继续用 24 小时。

### 解决方案：黑名单

退出时把 token 存到数据库黑名单表，每次验证 token 时先查黑名单。

```go
// server/model/system/sys_jwt_blacklist.go
type SysJwtBlacklist struct {
    ID        uint64    `gorm:"primaryKey"`
    Token     string    `gorm:"column:token"`       // 原始 token
    TokenHash string    `gorm:"column:token_hash"`  // token 的 SHA256 哈希
    Username  string    `gorm:"column:username"`
    CreatedAt time.Time `gorm:"column:created_at"`
}
```

退出逻辑：

```go
// server/service/system/auth_service.go
func (s *AuthService) Logout(token string, username string) error {
    // 把 token 哈希后存到黑名单表
    tokenHash := sha256.Sum256([]byte(token))
    blacklist := SysJwtBlacklist{
        Token:     token,
        TokenHash: hex.EncodeToString(tokenHash[:]),
        Username:  username,
    }
    return blacklistRepo.Create(&blacklist)
}
```

验证时查黑名单：

```go
func (s *AuthService) IsTokenBlacklisted(token string) (bool, error) {
    tokenHash := sha256.Sum256([]byte(token))
    count := blacklistRepo.CountByHash(hex.EncodeToString(tokenHash[:]))
    return count > 0, nil
}
```

**为什么存哈希值？** 防止黑名单表泄露后，攻击者直接拿到原始 token。

### 性能考虑

每次请求都查一次数据库黑名单，会不会太慢？
- 可以加 Redis 缓存：黑名单 token 的哈希值存 Redis，查询时先查 Redis
- 但本项目用户量小，直接查 MySQL 也够用

## 五、角色权限：RBAC 简化版

### 三种角色

```go
// server/utils/roles.go
const (
    RoleAdmin   = "ADMIN"   // 超级管理员：所有权限
    RoleManager = "MANAGER" // 管理员：业务权限 + 配置管理
```

### 权限表

| 功能 | ADMIN | MANAGER | USER |
|---|---|---|---|
| 登录/退出/查看自己信息 | ✅ | ✅ | ✅ |
| 查看任务/总览/历史/预警 | ✅ | ✅ | ✅ |
| 创建/删除任务 | ✅ | ✅ | ❌ |
| 修改安全配置 | ✅ | ✅ | ❌ |
| 用户管理 | ✅ | ❌ | ❌ |
| 审计日志 | ✅ | ❌ | ❌ |
| 实时监控观察面板 | ✅ | ✅ | ❌ |
| 个人实时监控 | ✅ | ✅ | ✅ |

### 后端：中间件做权限控制

```go
// server/router/security/config.go
func InitConfigRouter(Router *gin.RouterGroup) {
    configRouter := Router.Group("configs")
    configRouter.Use(middleware.RequireRoles("ADMIN", "MANAGER"))  // ← 只有 ADMIN 和 MANAGER 能访问
    {
        configRouter.GET("security", configApi.GetSecurityConfig)
        configRouter.PUT("security", configApi.UpdateSecurityConfig)
    }
}
```

`RequireRoles` 中间件：

```go
// server/middleware/jwt.go
func RequireRoles(roleCodes ...string) gin.HandlerFunc {
    return func(c *gin.Context) {
        value, _ := c.Get("claims")
        claims := value.(*utils.TokenClaims)

        for _, roleCode := range roleCodes {
            if claims.RoleCode == roleCode {
                c.Next()  // 角色匹配，放行
                return
            }
        }
        c.JSON(403, response.Fail("无权访问当前资源"))
        c.Abort()
    }
}
```

### 前端：路由守卫做权限控制

```javascript
// web/src/router/index.js
router.beforeEach(async (to, from, next) => {
    const userStore = useUserStore()

    // 1. 判断是否需要登录
    if (to.meta.requiresAuth && !userStore.token) {
        next('/login')
        return
    }

    // 2. 如果有 token 但没拉过用户信息，先拉取
    if (userStore.token && !userStore.userInfo.username) {
        await userStore.getCurrentUser()
    }

    // 3. 检查角色权限
    if (to.meta.roles && !to.meta.roles.includes(userStore.userInfo.roleCode)) {
        ElMessage.error('当前账号无权访问此页面')
        next('/security/overview')
        return
    }

    next()
})
```

路由定义时标记权限：

```javascript
// web/src/router/modules/security.js
{
    path: '/security/config',
    component: () => import('@/view/security/config/index.vue'),
    meta: {
        requiresAuth: true,
        roles: ['ADMIN', 'MANAGER'],  // ← 只有这两种角色能访问
    },
}
```

### 关键原则

**前端权限只是用户体验，后端权限才是安全边界**。

为什么？因为前端代码可以被绕过（用户直接改 localStorage 里的 roleCode，或者直接用 Postman 调接口）。所以：
- 前端做权限是为了**不显示按钮**，避免误操作
- 后端做权限是为了**真正拦截请求**，防止越权

## 六、密码安全

项目里密码不是明文存的，而是 bcrypt 哈希：

```go
// server/model/system/sys_user.go
func (u *SysUser) CheckPassword(password string) bool {
    err := bcrypt.CompareHashAndPassword([]byte(u.PasswordHash), []byte(password))
    return err == nil
}

func HashPassword(password string) string {
    hash, _ := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)
    return string(hash)
}
```

**为什么用 bcrypt 不用 MD5？**
- MD5 太快，可以暴力破解
- bcrypt 故意做得很慢（默认 10 次迭代），而且每次哈希结果不同（加了随机盐）

```go
type SysLoginLog struct {
```

## 八、本章 Q&A

**Q：JWT 和 Session 有什么区别？为什么选 JWT？**
A：
- Session 是有状态的：服务端存 sessionId → userInfo 的映射，每次请求都查
- JWT 是无状态的：用户信息直接编码在 token 里，服务端不用存

选 JWT 的原因：
1. 前后端分离项目，天然适合 token 认证
2. 不用维护 session 存储，部署简单
3. 跨域友好

缺点：
1. token 一旦签发，过期前都有效（所以加了黑名单）
2. token 体积比 sessionId 大

**Q：为什么要做 JWT 黑名单？直接让 token 过期不就行了？**
A：场景：用户发现自己的账号被盗了，想立刻让所有已签发的 token 失效。如果只靠过期时间，只能等 24 小时。黑名单可以立即让 token 失效。

**Q：如果黑名单表数据量很大怎么办？**
A：
1. 定期清理已过期的 token（反正过期后本来就不能用）
2. 只存 token 哈希值，不存原始 token，节省空间
3. 用 Redis 做黑名单缓存，减少数据库压力

**Q：为什么角色只有三种？如果业务复杂了怎么办？**
A：本项目是简化版 RBAC（Role-Based Access Control），只有用户 → 角色 → 权限三层。如果业务复杂，可以加：
- 权限表（permissions）：`create_task`、`delete_task`、`view_dashboard`
- 角色-权限关联表：一个角色对应多个权限
- 用户-角色关联表：一个用户可以有多个角色

**Q：前端路由守卫和后端中间件，哪个先做权限校验？**
A：请求流程：浏览器 → 前端路由守卫 → 发请求 → 后端 JWT 中间件 → 后端角色中间件 → 业务处理。

前端守卫先执行（页面级），后端中间件后执行（接口级）。两者都要做，不能省。
