# 07. 实时流量监控：独立监听会话

## 一、本章要解决的问题

第 6 章讲的流量增强是**绑定任务**的：用户创建任务 → 系统解析 pcap → 写入流量三表 → 任务详情展示。

但有一个场景没覆盖：**用户想实时监控本机网卡流量，看有没有异常**，不需要创建任务。

本章讲：实时流量监控这条独立链路。

## 二、为什么实时监控是独立的？

对比两条链路：

| 维度 | 任务流量增强 | 实时流量监控 |
|---|---|---|
| 触发方式 | 创建任务时自动执行 | 用户手动启动 |
| 数据来源 | pcap 文件 / 在线抓包（短时） | 网卡实时监听（持续） |
| 绑定任务 ID | ✅ 是 | ❌ 否 |
| 写入流量三表 | ✅ 是 | ❌ 否 |
| 预警方式 | 评分 >= 75 触发预警 | 行为分 >= 75 触发预警 |
| 预警来源 | `sourceType = TASK` | `sourceType = FLOW_MONITOR` |
| 页面入口 | 任务详情页 | `/security/monitor` 独立页面 |

**核心区别**：任务流量是"一次性分析"，实时监控是"持续监听"。

## 三、整体流程

```
用户在前端选择网卡，点击"开始监控"
    ↓
POST /api/v1/flow-monitor/sessions  {interfaceName: "eth0"}
    ↓
后端创建会话记录（内存中）
    ↓
启动 goroutine：
    打开网卡 → 每 5 秒统计一次 → 计算行为风险分 → 判断预警
    ↓
前端轮询 GET /sessions/:id 获取实时数据
    ↓
用户点击"停止监控" → POST /sessions/:id/stop
```

## 四、核心代码走读

文件：`server/service/security/flow_monitor_service.go`

### 1. 启动会话

```go
func (s *FlowMonitorService) StartSession(userID uint64, interfaceName string) (FlowMonitorSession, error) {
    // 1. 检查是否已有运行中的会话
    if existing := s.findRunningSession(userID); existing != nil {
        return FlowMonitorSession{}, errors.New("已有运行中的监控会话")
    }

    // 2. 创建会话
    session := FlowMonitorSession{
        ID:            generateSessionID(),
        UserID:        userID,
        InterfaceName: interfaceName,
        Status:        "RUNNING",
        StartedAt:     time.Now(),
    }
    s.sessions[session.ID] = &session

    // 3. 启动 goroutine 采集
    go s.runSession(session.ID)

    return session, nil
}
```

**会话存哪里？** 内存中的 map，不存数据库。

**为什么不存数据库？**
- 会话是临时的，停止后就没用了
- 存数据库会增加 IO 开销
- 进程重启后会话本来就应该清空

**缺点**：进程重启，正在监控的会话会丢失。

### 2. 采集循环

```go
func (s *FlowMonitorService) runSession(sessionID string) {
    session := s.sessions[sessionID]

    // 1. 打开网卡
    handle, err := pcap.OpenLive(session.InterfaceName, 1600, true, pcap.BlockForever)
    if err != nil {
        session.Status = "FAILED"
        session.ErrorMessage = err.Error()
        return
    }
    defer handle.Close()

    // 2. 每 5 秒统计一次
    ticker := time.NewTicker(5 * time.Second)
    defer ticker.Stop()

    packetSource := gopacket.NewPacketSource(handle, handle.LinkType())
    packetChan := packetSource.Packets()

    window := &WindowStats{}  // 当前窗口的统计

    for {
        select {
        case packet := <-packetChan:
            window.ProcessPacket(packet)

        case <-ticker.C:
            // 5 秒到了，统计本窗口
            metrics := window.BuildMetrics()
            behaviorRisk := calculateBehaviorRisk(metrics)

            // 保存到会话历史
            session.Metrics = append(session.Metrics, metrics)
            session.BehaviorRisk = behaviorRisk

            // 判断预警
            if behaviorRisk >= 75 {
                s.createAlertIfNeeded(session, behaviorRisk, metrics)
            }

            // 重置窗口
            window = &WindowStats{}

        case <-session.StopChan:
            session.Status = "STOPPED"
            return
        }
    }
}
```

**关键点**：
- 每 5 秒一个窗口，统计报文数、协议分布、行为分
- 窗口数据保存在会话的 `Metrics` 数组里，前端可以画趋势图
- 达到阈值就生成预警

### 3. 预警指纹去重

问题：如果持续高风险，每 5 秒都生成一条预警，预警中心会被刷屏。

解决：**预警指纹 + 冷却时间**

```go
func (s *FlowMonitorService) createAlertIfNeeded(session *FlowMonitorSession, behaviorRisk float64, metrics Metrics) {
    // 1. 生成预警指纹（网卡 + 风险等级 + 时间窗口）
    fingerprint := fmt.Sprintf("%s-%s-%s",
        session.InterfaceName,
        mapRiskLevel(behaviorRisk),
        time.Now().Format("200601021504"),  // 精确到分钟
    )

    // 2. 检查是否已有相同指纹的预警
    if s.hasRecentAlert(fingerprint, 5*time.Minute) {
        return  // 5 分钟内已有相同预警，跳过
    }

    // 3. 创建预警
    alert := securityModel.AlertRecord{
        TaskID:      0,  // ← 实时监控没有任务 ID
        ScoreID:     nil,
        IP:          session.InterfaceName,
        AlertLevel:  mapRiskLevel(behaviorRisk),
        AlertTitle:  fmt.Sprintf("实时流量监控预警：%s", session.InterfaceName),
        AlertContent: fmt.Sprintf("行为风险分 %.2f，超过高风险阈值", behaviorRisk),
        Channel:     "SYSTEM",
        SourceType:  "FLOW_MONITOR",  // ← 标记来源
        SendStatus:  "PENDING",
    }
    repo.AlertRepository.Create(global.DB, &alert)

    // 4. 记录指纹
    s.alertFingerprints[fingerprint] = time.Now()
}
```

**指纹设计**：
- 同一网卡 + 同一风险等级 + 同一分钟 → 只生成一条预警
- 冷却时间 5 分钟 → 避免高频刷屏

**核心功能**：
1. 网卡下拉框（调用 `GET /configs/security/flow-interfaces` 枚举网卡）
2. "开始监控" / "停止监控" 按钮

## 七、和任务流量增强的对比

| 对比项 | 任务流量增强 | 实时流量监控 |
|---|---|---|
| 生命周期 | 任务创建 → 执行 → 完成 | 启动 → 持续运行 → 停止 |
| 数据保存 | 写入流量三表，永久保存 | 只在内存，停止后丢失 |
| 预警关联 | 关联任务 ID 和评分 ID | 无关联，`sourceType=FLOW_MONITOR` |
| 页面入口 | 任务详情页流量卡片 | 独立监控页 |
| 多用户隔离 | 通过任务 ID 区分 | 通过 userID 区分 |
| 历史回溯 | ✅ 可以查历史任务的流量 | ❌ 停止后数据丢失 |

## 八、为什么不写入流量三表？

如果实时监控也写入 `sec_flow_collection` 等三表：
- 每 5 秒写一次，1 小时写 720 条，1 天写 17280 条
- 表会快速膨胀
- 大部分数据没人看（用户只关心实时监控，不关心 1 小时前的）

**取舍**：实时监控只保留**内存中的最近 N 个窗口**（比如最近 100 个），不写数据库。预警记录写库，因为预警是重要的。

## 九、本章 Q&A

**Q：如果用户启动监控后关闭浏览器，后端 goroutine 会一直跑吗？**
A：会。goroutine 不依赖前端连接。

改进方案：
1. 加心跳机制：前端每 30 秒发一次心跳，后端 3 次没收到心跳就自动停止
2. 加超时：监控最多运行 1 小时，超时自动停止

**Q：实时监控会不会占用大量 CPU？**
A：取决于流量大小。
- 家用网络：每秒几十到几百个包，CPU 占用 < 1%
- 服务器网络：每秒几千到几万个包，CPU 占用可能 10%~30%

优化：
1. 用 BPF 过滤器只抓感兴趣的流量
2. 限制抓包速率（`pcap.SetSamplingRate`）
3. 限制会话历史长度（只保留最近 100 个窗口）

**Q：为什么预警指纹要包含时间窗口？**
A：如果不包含时间窗口，同一网卡同一风险等级永远只生成一条预警，后续风险变化时无法再次预警。

加上时间窗口（精确到分钟），可以保证：
- 同一分钟内不重复预警
- 过了 1 分钟后，如果风险仍然高，可以再预警一次

**Q：如果多用户同时监控同一网卡会怎样？**
A：当前实现允许，但不推荐。因为：
1. 同一网卡只能打开一次（pcap.OpenLive 会失败）
2. 多用户看到的数据一样，浪费资源

改进：启动前检查该网卡是否已被监控。

**Q：实时监控和 IDS（如 Snort）有什么区别？**
A：
- IDS：专业入侵检测系统，有几千条规则，能识别具体攻击类型（SQL 注入、XSS、缓冲区溢出）
- 本项目：轻量级流量统计 + 阈值判断，只能识别"流量异常"，不能识别具体攻击类型
