# 09. 数据库设计：13 张表的关系和理由

## 一、本章要解决的问题

为什么是 13 张表而不是 1 张大宽表？外键、索引、JSON 字段都是怎么考虑的？

## 二、表清单

### 系统域（3 张）

| 表名 | 用途 | 关键字段 |
|---|---|---|
| `sys_user` | 用户 | username, password_hash, role_code, enable |
| `sys_jwt_blacklist` | JWT 黑名单 | token, token_hash, username |
| `sys_login_log` | 登录日志 | username, ip, status, error_message |

### 安全域（10 张）

| 表名 | 用途 | 关键字段 |
|---|---|---|
| `sec_ip_task` | 任务主表 | task_no, target_ip, task_status |
| `sec_ip_base_info` | 基础画像 | country, region, isp, raw_payload |
| `sec_feature_snapshot` | 特征快照 | reputation_score, open_port_count, normalized_features |
| `sec_risk_score` | 风险评分 | score_value, risk_level, score_reason, weight_profile |
| `sec_alert_record` | 预警记录 | alert_level, alert_title, source_type |
| `sec_security_config` | 安全配置 | high_risk_threshold, weights, flow_mode |
| `sec_audit_log` | 审计日志 | category, action, actor, target_type |
| `sec_flow_collection` | 流量采集元数据 | collection_mode, packet_count, byte_count |
| `sec_flow_window_aggregate` | 流量窗口聚合 | window_no, packet_count, tcp_packet_count |
| `sec_flow_feature_snapshot` | 流量特征快照 | behavior_risk_score, protocol_distribution, dns_top_questions |


## 四、核心表详解

### 1. sec_ip_task（任务主表）

```sql
CREATE TABLE `sec_ip_task` (
  `id` BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  `task_no` VARCHAR(64) NOT NULL COMMENT '任务编号',
  `input_type` VARCHAR(16) DEFAULT 'IP' COMMENT 'IP / DOMAIN',
  `input_value` VARCHAR(255) COMMENT '原始输入值',
  `target_ip` VARCHAR(64) NOT NULL COMMENT '目标 IP',
  `created_by` VARCHAR(64) NOT NULL COMMENT '发起人',
  `task_status` VARCHAR(32) NOT NULL COMMENT 'PENDING/RUNNING/SUCCESS/FAILED',
  `error_message` VARCHAR(500) COMMENT '失败原因',
  `started_at` DATETIME,
  `finished_at` DATETIME,
  `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY `uk_sec_ip_task_task_no` (`task_no`),
  KEY `idx_sec_ip_task_target_ip` (`target_ip`),
  KEY `idx_sec_ip_task_created_by` (`created_by`),
  KEY `idx_sec_ip_task_status` (`task_status`),
  KEY `idx_sec_ip_task_created_at` (`created_at`)
)
```

**设计要点**：
- `task_no` 唯一索引：任务编号全局唯一
- `target_ip` 普通索引：按 IP 查询任务历史
- `task_status` 普通索引：筛选 RUNNING / FAILED 任务
- `created_at` 普通索引：按时间排序

**为什么不加外键关联 `sys_user`？**
- `created_by` 存的是 username 字符串，不是 user_id
- 用户删除后，任务记录的 `created_by` 仍然有效
- 避免级联删除任务

### 2. sec_ip_base_info（基础画像表）

```sql
CREATE TABLE `sec_ip_base_info` (
  `id` BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  `task_id` BIGINT UNSIGNED NOT NULL,
  `ip` VARCHAR(64) NOT NULL,
  `country` VARCHAR(64),
  `region` VARCHAR(64),
  `city` VARCHAR(64),
  `isp` VARCHAR(128),
  `whois_org` VARCHAR(255),
  `whois_contact` VARCHAR(255),
  `raw_payload` JSON COMMENT '原始返回内容',
  `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP,
  `updated_at` DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY `uk_sec_ip_base_info_task_id` (`task_id`),
  KEY `idx_sec_ip_base_info_ip` (`ip`),
  FOREIGN KEY (`task_id`) REFERENCES `sec_ip_task` (`id`)
)
```

**设计要点**：
- `task_id` 唯一索引：一个任务只有一条画像
- `raw_payload` JSON：保存 GeoLite2 / RDAP 原始返回，方便后续分析
- 外键关联 `sec_ip_task`

**为什么要 `raw_payload` JSON 字段？**
- GeoLite2 返回的字段很多（经纬度、时区、精度半径），不都要存成列
- JSON 字段灵活，后续要加新字段不用改表结构
- MySQL 5.7+ 支持 JSON 类型和 JSON 函数查询

### 3. sec_risk_score（风险评分表）

```sql
CREATE TABLE `sec_risk_score` (
  `id` BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  `task_id` BIGINT UNSIGNED NOT NULL,
  `ip` VARCHAR(64) NOT NULL,
  `base_score` DECIMAL(10,2) DEFAULT 0 COMMENT '基础属性贡献分',
  `reputation_score` DECIMAL(10,2) DEFAULT 0 COMMENT '信誉贡献分',
  `attack_surface_score` DECIMAL(10,2) DEFAULT 0,
  `behavior_score` DECIMAL(10,2) DEFAULT 0,
  `rule_adjustment_value` DECIMAL(10,2) DEFAULT 0,
  `score_value` DECIMAL(10,2) NOT NULL COMMENT '最终分',
  `risk_level` VARCHAR(32) NOT NULL COMMENT 'LOW/MEDIUM/HIGH/CRITICAL',
  `score_reason` VARCHAR(500) COMMENT '评分原因',
  `rule_adjustment` VARCHAR(255) COMMENT '规则修正说明',
  `algorithm_version` VARCHAR(128) COMMENT '算法版本',
  `weight_profile` JSON COMMENT '权重配置快照',
  `is_alert_triggered` TINYINT(1) DEFAULT 0,
  `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY `uk_sec_risk_score_task_id` (`task_id`),
  KEY `idx_sec_risk_score_ip` (`ip`),
  KEY `idx_sec_risk_score_score_value` (`score_value`),
  KEY `idx_sec_risk_score_risk_level` (`risk_level`),
  KEY `idx_sec_risk_score_created_at` (`created_at`),
  FOREIGN KEY (`task_id`) REFERENCES `sec_ip_task` (`id`)
)
```

**设计要点**：
- 保存每个维度的贡献分（`base_score`、`reputation_score` 等），方便解释
- 保存 `weight_profile` JSON：记录评分时的权重配置，历史评分用历史权重
- 保存 `algorithm_version`：算法版本号，方便追溯

### 4. sec_alert_record（预警记录表）

```sql
CREATE TABLE `sec_alert_record` (
  `id` BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  `task_id` BIGINT UNSIGNED COMMENT '关联任务 ID（实时监控预警为 0）',
  `score_id` BIGINT UNSIGNED COMMENT '关联评分 ID（实时监控预警为 NULL）',
  `ip` VARCHAR(64) NOT NULL,
  `alert_level` VARCHAR(32) NOT NULL,
  `alert_title` VARCHAR(255) NOT NULL,
  `alert_content` TEXT,
  `channel` VARCHAR(32) NOT NULL COMMENT '通知渠道（SYSTEM/EMAIL）',
  `send_status` VARCHAR(32) NOT NULL COMMENT 'PENDING/SENT/FAILED',
  `send_time` DATETIME,
  `source_type` VARCHAR(32) DEFAULT 'TASK' COMMENT 'TASK / FLOW_MONITOR',
  `created_at` DATETIME DEFAULT CURRENT_TIMESTAMP,
  KEY `idx_sec_alert_record_task_id` (`task_id`),
  KEY `idx_sec_alert_record_ip` (`ip`),
  KEY `idx_sec_alert_record_alert_level` (`alert_level`),
  KEY `idx_sec_alert_record_send_status` (`send_status`),
  KEY `idx_sec_alert_record_created_at` (`created_at`),
  FOREIGN KEY (`task_id`) REFERENCES `sec_ip_task` (`id`),
  FOREIGN KEY (`score_id`) REFERENCES `sec_risk_score` (`id`)
)
```

**设计要点**：
- `task_id` 允许为 0：实时监控预警没有任务 ID
- `score_id` 允许为 NULL：实时监控预警没有评分 ID
- `source_type` 区分预警来源：`TASK` / `FLOW_MONITOR`
- `send_status` 跟踪通知发送状态

### 5. 流量三表

#### sec_flow_collection（采集元数据）

```sql
CREATE TABLE `sec_flow_collection` (
  `id` BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  `task_id` BIGINT UNSIGNED NOT NULL,
  `ip` VARCHAR(64) NOT NULL,
  `collection_mode` VARCHAR(32) COMMENT 'offline_pcap / online_capture',
  `collection_status` VARCHAR(32) COMMENT 'PARSED / FAILED',
  `parser_name` VARCHAR(128),
  `pcap_file_path` VARCHAR(255),
  `packet_count` BIGINT UNSIGNED DEFAULT 0,
  `byte_count` BIGINT UNSIGNED DEFAULT 0,
  `conversation_count` INT UNSIGNED DEFAULT 0,
  `summary` VARCHAR(500),
  `error_message` VARCHAR(500),
  `evidence_payload` JSON,
  KEY `idx_sec_flow_collection_task_id` (`task_id`),
  KEY `idx_sec_flow_collection_ip` (`ip`),
  FOREIGN KEY (`task_id`) REFERENCES `sec_ip_task` (`id`)
)
```

#### sec_flow_window_aggregate（窗口聚合）

```sql
CREATE TABLE `sec_flow_window_aggregate` (
  `id` BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  `collection_id` BIGINT UNSIGNED NOT NULL,
  `task_id` BIGINT UNSIGNED NOT NULL,
  `window_no` INT UNSIGNED NOT NULL,
  `window_start` DATETIME NOT NULL,
  `window_end` DATETIME NOT NULL,
  `packet_count` BIGINT UNSIGNED DEFAULT 0,
  `tcp_packet_count` BIGINT UNSIGNED DEFAULT 0,
  `udp_packet_count` BIGINT UNSIGNED DEFAULT 0,
  `dns_event_count` INT UNSIGNED DEFAULT 0,
  `http_event_count` INT UNSIGNED DEFAULT 0,
  `tls_event_count` INT UNSIGNED DEFAULT 0,
  UNIQUE KEY `uk_sec_flow_window_collection_window` (`collection_id`, `window_no`),
  KEY `idx_sec_flow_window_task_window_start` (`task_id`, `window_start`),
  FOREIGN KEY (`collection_id`) REFERENCES `sec_flow_collection` (`id`),
  FOREIGN KEY (`task_id`) REFERENCES `sec_ip_task` (`id`)
)
```

**设计要点**：
- `(collection_id, window_no)` 联合唯一索引：一个采集的窗口编号唯一
- `(task_id, window_start)` 联合索引：按任务和时间查询窗口

#### sec_flow_feature_snapshot（特征快照）

```sql
CREATE TABLE `sec_flow_feature_snapshot` (
  `id` BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  `collection_id` BIGINT UNSIGNED NOT NULL,
  `task_id` BIGINT UNSIGNED NOT NULL,
  `behavior_risk_score` DECIMAL(10,2),
  `peak_pps` DECIMAL(12,2),
  `burst_score` DECIMAL(10,2),
  `scan_score` DECIMAL(10,2),
  `protocol_distribution` JSON,
  `dns_top_questions` JSON,
  `http_host_hints` JSON,
  `tls_handshake_hints` JSON,
  `directionality_indicators` JSON,
  `port_density_indicators` JSON,
  `payload_entropy_indicators` JSON,
  UNIQUE KEY `uk_sec_flow_feature_snapshot_collection_id` (`collection_id`),
  FOREIGN KEY (`collection_id`) REFERENCES `sec_flow_collection` (`id`),
  FOREIGN KEY (`task_id`) REFERENCES `sec_ip_task` (`id`)
)
```

## 五、设计原则总结

### 1. 为什么不用大宽表？

如果合成一张大宽表：

```sql
CREATE TABLE sec_task_full (
  id, task_no, target_ip, task_status,
  country, region, isp,
  reputation_score, open_port_count,
  base_score, reputation_score_contrib, attack_surface_score_contrib,
  behavior_score_contrib, rule_adjustment_value, score_value, risk_level,
  alert_level, alert_title,
  collection_mode, packet_count, byte_count,
  -- ... 50+ 列
)
```

**缺点**：
1. 列太多，查询和维护都麻烦
2. 不是所有任务都有流量数据，很多字段是 NULL
3. 更新某一部分时要锁整行

### 2. 为什么用 JSON 字段？

**适合 JSON 的场景**：
- 字段不固定（GeoLite2 返回的字段很多）
- 嵌套结构（`protocol_distribution: {"TCP":800,"UDP":300}`）
- 不需要按字段查询（只查询整个 JSON）

**不适合 JSON 的场景**：
- 需要按字段筛选（如 `WHERE country = 'CN'`）
- 需要按字段排序（如 `ORDER BY score_value DESC`）

项目里的选择：
- 核心查询字段（IP、分数、等级）→ 独立列 + 索引
- 扩展字段（原始返回、协议分布）→ JSON

### 3. 为什么加外键？

**好处**：
- 保证数据一致性：不能插入 `task_id = 999` 的画像，如果任务表里没有 ID 999
- 删除时级联检查：删除任务时，数据库会检查是否有关联画像

**缺点**：
- 写入性能略低（要检查外键约束）
- 分库分表时不方便

本项目数据量小，单体数据库，用外键合适。

### 4. 索引策略

**主键索引**：所有表都有 `id BIGINT PRIMARY KEY AUTO_INCREMENT`

**唯一索引**：
- `task_no`：任务编号全局唯一
- `task_id`（在画像/特征/评分表）：一个任务只有一条画像/特征/评分
- `(collection_id, window_no)`：一个采集的窗口编号唯一

**普通索引**：
- 常用筛选字段：`target_ip`、`task_status`、`risk_level`、`alert_level`
- 排序字段：`created_at`

**联合索引**：
- `(task_id, window_start)`：查询某任务的窗口趋势

## 六、本章 Q&A

**Q：为什么 `created_at` 和 `updated_at` 用 DATETIME 不用 TIMESTAMP？**
A：
- DATETIME 范围：1000-01-01 到 9999-12-31
- TIMESTAMP 范围：1970-01-01 到 2038-01-19（32 位时间戳）
- DATETIME 不受时区影响，TIMESTAMP 会自动转时区

项目用 DATETIME 更安全。

**Q：为什么分数用 DECIMAL 不用 FLOAT？**
A：
- FLOAT 是近似值，`0.1 + 0.2 != 0.3`
- DECIMAL 是精确值，适合金融和评分场景

**Q：如果任务量很大（百万级），表会不会很慢？**
A：会。优化方案：
1. 分表：按月份分表（`sec_ip_task_202604`、`sec_ip_task_202605`）
2. 归档：3 个月前的任务移到历史表
3. 读写分离：查询走从库，写入走主库
4. ES 索引：任务详情存 MySQL，列表查询走 Elasticsearch

**Q：为什么预警表允许 `task_id = 0`？**
A：实时监控预警不绑定任务，用 `task_id = 0` 和 `source_type = 'FLOW_MONITOR'` 标记。

**Q：如果让我重新设计，会改哪里？**
A：
1. 把 `created_by` 改成 `user_id`，加外键关联 `sys_user`
2. 流量三表加分区（按 `created_at` 月分区）
3. 加 `deleted_at` 软删除字段，避免误删
