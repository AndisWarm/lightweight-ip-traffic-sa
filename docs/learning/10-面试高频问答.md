# 10. 面试高频问答速查

> 本章是面试前的最后一遍复习材料。按主题分类，每题给出**简短答案**（30 秒内说完）+ **深挖追问**（如果面试官继续问）。

## 一、项目整体

### Q1：你的项目是做什么的？

**简短答案**：
这是一个轻量化的 IP 态势感知系统。用户输入一个 IP，系统从四个维度采集数据：基础画像（GeoLite2/RDAP）、信誉风险（黑名单/AbuseIPDB）、攻击面（端口探测/Nmap）、流量行为（gopacket 解析 pcap），然后用加权评分模型算出 0~100 的风险分，超过 75 分就触发预警。

**深挖追问**：
- 为什么叫"轻量化"？→ 不依赖重型安全平台，外部数据源都是可选的，主链路只需要 MySQL + Redis
- 为什么叫"态势感知"？→ 融合静态画像、历史信誉、当前暴露、动态行为四个维度，形成对 IP 风险的整体认知

### Q2：你在项目中负责什么？

**简短答案**：
我负责核心业务链路建设和前后端联调：后端任务创建、采集编排、评分、预警、缓存、配置管理，前端安全任务、总览、历史、预警、配置页面的接口对接和可视化。还参与了需求分析、数据库设计、部署验证和文档整理。

### Q3：项目最大的难点是什么？

**简短答案**：
最大的难点是把多源采集、评分、预警、任务状态、缓存和流量增强统一到一条稳定链路里。不同数据源稳定性不同（GeoLite2 本地、RDAP 公网、Nmap 依赖环境），流量能力还依赖 Npcap 和权限。解决思路是：分层、接口抽象、超时控制、失败降级、事务写入。

**深挖追问**：
- 具体怎么处理外部源失败？→ 每个数据源都有 fallback，失败时记录降级原因但不阻断任务
- 为什么用事务？→ 任务结果涉及 7 张表，必须保证要么全成功要么全失败

## 二、技术架构

### Q4：为什么后端用 Go 不用 Java/Python？

**简短答案**：
1. Go 编译成单二进制，部署简单，不需要 JVM 或 Python 环境
2. Go 的 goroutine 适合做并发采集（同时查 GeoLite2、RDAP、扫端口）
3. Go 生态里 gopacket 是成熟的 pcap 解析库

**深挖追问**：
- Go 有什么缺点？→ 泛型支持晚（1.18 才有）、错误处理啰嗦（每个 err 都要判断）、依赖管理不如 Maven 成熟

### Q5：为什么用 Gin 不用 Echo/Beego？

**简短答案**：
Gin 是 Go 生态使用最广的 HTTP 框架，文档全、社区活跃、性能足够。这个项目框架不是瓶颈，生态和开发效率更重要。

### Q6：为什么用 Gorm 不用原生 SQL？

**简短答案**：
Gorm 把 CRUD 写得很快，事务、关联查询、自动迁移都有现成方法。缺点是会隐藏 SQL，性能敏感场景需要看生成的 SQL。本项目是 CRUD 密集型，Gorm 合适。

### Q7：为什么前端用 Vue3 不用 React？

**简短答案**：
Vue3 的组合式 API 和响应式系统适合中后台，模板语法更接近 HTML，学习曲线平缓。Element Plus 组件库在 Vue 生态里最成熟。

### Q8：后端分层是怎么做的？

**简短答案**：
五层：router（URL 分组）→ api/v1（参数绑定 + 统一响应）→ service（业务编排）→ repository（数据访问）→ model（实体/请求/响应）。每层职责单一，改一层不影响其他层。

**深挖追问**：
- Service 和 Repository 为什么要分开？→ Service 写业务时不用关心 SQL，单元测试时可以 mock Repository

## 三、登录鉴权

### Q9：JWT 是什么？为什么用它？

**简短答案**：
JWT 是一段加密字符串，包含 Header、Payload、Signature 三部分。Payload 里有用户名、角色、过期时间。用它的原因：无状态（服务端不用存 session）、跨域友好、前后端分离天然适合。

**深挖追问**：
- JWT 有什么缺点？→ 一旦签发，过期前都有效。所以加了黑名单处理登出。

### Q10：为什么要做 JWT 黑名单？

**简短答案**：
JWT 是无状态的，用户登出后只删前端 token，已经泄露的 token 仍可用。黑名单把登出的 token 存到数据库，每次鉴权时先查黑名单，立即失效。

**深挖追问**：
- 黑名单会不会成为性能瓶颈？→ 当前用户量小，直接查 MySQL 够用。如果量大，可以用 Redis 缓存黑名单哈希值。

### Q11：权限怎么做的？

**简短答案**：
三种角色：ADMIN（所有权限）、MANAGER（业务权限 + 配置）、USER（只读业务页面）。后端用 `RequireRoles` 中间件做接口级控制，前端用路由守卫做页面级控制。**真正的安全边界是后端**，前端只是用户体验。

## 四、核心任务链路

### Q12：创建任务后发生了什么？

**简短答案**：
1. 校验 IP/域名，写任务表（PENDING → RUNNING）
2. 清理总览缓存
3. 启动 goroutine 异步采集四维数据、归一化、加权评分、规则修正
4. 事务写入 7 张表（画像、特征、评分、预警、流量三表）
5. 更新任务状态为 SUCCESS，写审计日志

**深挖追问**：
- 为什么异步？→ 采集可能涉及外部 API 和端口探测，耗时不可控。同步会卡接口，异步可以秒回 taskID
- 为什么用 goroutine 不用消息队列？→ goroutine 简单，不用引入额外组件。缺点是进程重启会丢任务

### Q13：任务状态有哪些？

**简短答案**：
PENDING（已创建）→ RUNNING（执行中）→ SUCCESS（成功）/ FAILED（失败）。删除是直接 DELETE SQL，不是状态变更。

### Q14：如果采集过程中 RDAP 超时了怎么办？

**简短答案**：
不会让任务失败。RDAP 是增强数据源，超时会记录降级原因，继续用 GeoLite2 的数据。只有所有数据源都失败或参数错误时，任务才会 FAILED。

**深挖追问**：
- 降级会不会影响评分准确性？→ 会。但这是"可用性 vs 准确性"的取舍，系统优先保证主链路可用。

## 五、数据源采集

### Q15：GeoLite2 和 RDAP 分别解决什么问题？

**简短答案**：
GeoLite2 是本地离线数据库，查询 IP 的国家、城市、ASN、ISP。RDAP 是公网 API，查询 IP 的注册组织、网段、联系人。GeoLite2 快且稳定，RDAP 补充注册信息。

### Q16：为什么本地黑名单是主方案，AbuseIPDB 是增强？

**简短答案**：
AbuseIPDB 需要 API Key，有调用次数限制，依赖公网。本地黑名单离线可用，可以自己维护。AbuseIPDB 失败时回退到本地黑名单。

### Q17：端口探测为什么不扫全部 65535 个端口？

**简短答案**：
1. 太慢：65535 个端口 × 800ms 超时 = 最长 14 小时
2. 太重：容易被目标防火墙识别为扫描并封锁
3. 没必要：常见高危服务就那几个端口（22/445/3389/8080）

项目只扫 6 个端口，控制并发数（3 个）和超时（800ms）。

### Q18：Nmap 在项目中是什么定位？

**简短答案**：
Nmap 是攻击面增强能力，不是默认依赖。未安装或执行失败时，回退到 Go 原生的有限端口探测。这样普通开发环境也能跑，有安全测试环境时可以增强。

## 六、评分算法

### Q19：评分模型是什么？

**简短答案**：
多维度加权 + 规则修正。四个维度：基础画像（0.20）、信誉（0.35）、攻击面（0.30）、行为（0.15）。加权求和得到核心分，再根据规则（地理风险 +6、高危端口 ≥3 +5、行为风险 ≥70 +8）修正，最后映射到 LOW/MEDIUM/HIGH/CRITICAL。

**深挖追问**：
- 权重怎么定的？→ 层次分析法（AHP）思想，主观定权重。信誉最高因为黑名单直接表达历史滥用，行为最低因为流量可用性受环境影响。
- 为什么不用机器学习？→ 数据集不够、可解释性差、教学价值。加权模型可以在白板手算。

### Q20：手算一个评分（面试官给你具体数据）

**示例**：俄罗斯 IP，ISP 是 Cloud Hosting，命中黑名单，开放 6 个端口其中 3 个高危，行为分 60。

**手算步骤**：
1. WhoisRisk = 25 + 30 + 15 = 70
2. ReputationRisk = 92
3. AttackSurfaceRisk = 6×4 + 3×15 + 10 = 79
4. BehaviorRisk = 60
5. CoreScore = 70×0.20 + 92×0.35 + 79×0.30 + 60×0.15 = 78.9
6. RuleAdjustment = +6（地理风险）+ +5（高危端口≥3）= 11
7. FinalScore = 78.9 + 11 = 89.9
8. 89.9 ≥ 75 → HIGH → 触发预警

### Q21：评分结果怎么保证可解释？

**简短答案**：
任务详情页展示每个维度的原始分、权重、贡献值、依据。例如"基础属性风险 70 分（权重 0.20，贡献 14 分），依据：命中地理风险国家 RU (+30)，ISP 为 Cloud Hosting (+15)"。还保存算法版本和权重配置快照。

## 七、流量增强

### Q22：gopacket 在项目中起什么作用？

**简短答案**：
gopacket 是 Go 的 pcap 解析库。离线模式读 pcap 文件，在线模式配合 Npcap 从网卡抓包。解析出网络层（IP）、传输层（TCP/UDP）、应用层（DNS/HTTP/TLS）特征，算出行为风险分。

### Q23：为什么不把流量分析作为默认硬依赖？

**简短答案**：
流量分析依赖环境：pcap 文件、Npcap、网卡权限、管理员权限。如果作为硬依赖，很多环境跑不起来。所以设计成可选增强能力，关闭时主链路仍可用。

### Q24：载荷熵是什么？为什么用它？

**简短答案**：
熵是信息论概念，表示数据随机性。加密、压缩、混淆的数据熵值高（7-8），明文数据熵值低（4-5）。恶意软件常用加密/混淆隐藏通信，所以高熵载荷是可疑信号。

**深挖追问**：
- 怎么算熵？→ 统计每个字节值（0-255）出现频率，用香农公式 `-Σ p×log2(p)`

### Q25：流量三表分别存什么？

**简短答案**：
- `sec_flow_collection`：采集元数据（模式、状态、pcap 路径、总报文数）
- `sec_flow_window_aggregate`：窗口聚合（按 60 秒窗口统计报文、协议、事件数）
- `sec_flow_feature_snapshot`：特征快照（行为分、协议分布、DNS/HTTP/TLS Top、方向性、端口密度、熵）

## 八、实时监控

### Q26：实时监控和任务流量增强有什么区别？

**简短答案**：
任务流量是绑定任务 ID 的一次性分析，写入流量三表。实时监控是独立链路，不绑定任务，不写三表，只在内存中保留最近 N 个窗口，达到阈值就生成预警。

### Q27：实时监控怎么处理预警刷屏？

**简短答案**：
预警指纹 + 冷却时间。指纹 = 网卡 + 风险等级 + 时间窗口（精确到分钟）。同一指纹 5 分钟内只生成一条预警。

## 九、缓存和降级

### Q28：Redis 挂了系统还能跑吗？

**简短答案**：
能跑。Redis 只是缓存，不是主存储。缓存失败时回退到 MySQL 查询或实时采集，只是性能下降。核心数据都在 MySQL。

### Q29：缓存 key 为什么要包含配置版本？

**简短答案**：
因为采集结果和评分受配置影响（权重、阈值、数据源开关）。配置变化后应该得到新结果，不能复用旧缓存。所以 key 包含 `target_ip + source_name + config_version`，配置变了 key 就变了。

### Q30：项目有哪些降级策略？

**简短答案**：
1. GeoLite2 缺失 → 用 RDAP 补充
2. RDAP 失败 → 记录降级原因，继续
3. AbuseIPDB 失败 → 回退本地黑名单
4. Nmap 失败 → 回退 Go 原生探测
5. 流量采集失败 → 标记失败状态，不阻断任务
6. Redis 失败 → 无缓存模式

核心原则：增强能力可降级，主链路永不阻断。

## 十一、深挖问题

### Q35：如果 Redis 和 MySQL 同时挂了怎么办？

**简短答案**：
系统无法运行。MySQL 是主存储，挂了所有业务都没法跑。Redis 挂了可以降级，MySQL 挂了必须退出。启动时 `InitDB()` 失败会直接 `log.Fatal`。

### Q36：如果用户并发创建 100 个任务会怎样？

**简短答案**：
goroutine 会爆。100 个并发采集会同时访问 GeoLite2、RDAP、端口探测，可能把外部服务打挂。改进：用信号量限制并发数（最多 10 个），或用任务队列按顺序执行。

### Q37：任务执行到一半，进程重启了怎么办？

**简短答案**：
当前实现：任务永远卡在 RUNNING。改进：启动时扫描 RUNNING 任务，超过 5 分钟没更新就标记为 FAILED 或重新执行。

### Q38：如果一个 IP 的评分很高，你怎么解释它为什么高？

**简短答案**：
从任务详情页的评分因子展开：基础画像是否命中高风险地区或托管 ISP，信誉是否命中黑名单，开放端口和高危端口数量是否异常，流量行为是否出现 DNS 激增、端口扫描、异常 TLS 或高熵载荷。结合规则调整说明和证据项解释最终风险等级。

### Q39：项目的数据一致性怎么保证？

**简短答案**：
1. 任务结果写入用事务：画像、特征、评分、预警、流量三表要么全成功要么全失败
2. 删除任务用事务：按顺序删除关联表，避免残留孤立数据
3. 外键约束：不能插入不存在任务的画像

### Q40：项目的安全性怎么保证？

**简短答案**：
1. 未登录访问：JWT 鉴权中间件
2. 退出后 token 继续使用：JWT 黑名单
3. 普通用户改敏感配置：后端角色中间件
4. 外部服务超时：上下文超时 + fallback
5. 缓存服务不可用：Redis 可选 + 数据库回退
6. 任务关联数据不一致：事务写入 + 关联删除
7. 安全操作不可追溯：审计日志

### Q42：你遇到的最大挑战是什么？怎么解决的？

**简短答案**：

### Q43：你为什么做这个项目？

**简短答案**：
毕业设计选题，想做一个结合网络安全和全栈开发的项目。IP 态势感知既有安全领域的专业性（多源采集、风险评分），又有全栈的完整性（前后端、数据库、缓存、部署）。

## 十三、自我介绍口径（背下来）

### 30 秒版

> 我做了一个轻量化的 IP 态势感知系统，技术栈是 Go + Gin + Gorm + MySQL + Redis 后端，Vue3 + Element Plus + ECharts 前端。核心是给任意 IP 算 0~100 的风险分：从 GeoLite2 查地理、黑名单查信誉、扫端口看攻击面、用 gopacket 解析 pcap 看流量行为，四维加权 + 规则修正，超过 75 分触发预警。系统支持任务异步执行、JWT 鉴权、角色权限、实时监控，主链路全部落地。

### 2 分钟版

> 在 30 秒基础上加：
> - 业务闭环：登录 → 创建任务 → 异步采集评分 → 总览/历史/预警 → 配置管理
> - 架构亮点：双域拆分（system + security）、五层架构（router → api → service → repository → model）
> - 可靠性：缓存降级、外部源 fallback、事务写入、JWT 黑名单
> - 流量能力：支持 pcap 离线解析和 Npcap 在线抓包，提取 DNS/HTTP/TLS/端口密度/方向性/载荷熵
> - 可解释性：每条评分都能拆到具体因子和权重，任务详情页展示来源链和证据项

## 十四、面试前 1 小时速查清单

1. **评分公式**：`FinalScore = Σ(四维风险×权重) + 规则修正(-5~+15)`
2. **默认权重**：whois 0.20 / reputation 0.35 / attackSurface 0.30 / behavior 0.15
3. **阈值**：≥90 CRITICAL、≥75 HIGH、≥45 MEDIUM
4. **任务状态**：PENDING → RUNNING → SUCCESS / FAILED
5. **流量三表**：collection（元数据）/ window_aggregate（窗口）/ feature_snapshot（特征）
6. **降级原则**：增强能力可降级，主链路永不阻断
7. **安全边界**：前端权限是用户体验，后端权限才是安全边界
8. **事务场景**：任务结果写入、任务删除
9. **缓存 key**：`target_ip + source_name + config_version`
10. **预警指纹**：`网卡 + 风险等级 + 时间窗口`，冷却 5 分钟
