# 05. 评分算法：从数据到风险等级（含手算示例）

## 一、本章要解决的问题

采集到四维数据后，怎么算出一个 0~100 的分数？为什么是 75 分触发预警而不是 80 分？权重 0.20/0.35/0.30/0.15 是怎么定的？

## 二、评分算法总览

```
四维原始数据
    ↓
[归一化] → 四个 0~100 的风险分
    ↓
[加权融合] → 核心分（CoreScore）
    ↓
[规则修正] → 最终分（FinalScore）
    ↓
[等级映射] → LOW / MEDIUM / HIGH / CRITICAL
    ↓
[预警判定] → 是否生成预警
```

## 三、第一步：归一化（原始数据 → 0~100 风险分）

### 1. 基础画像风险（WhoisRiskScore）

**输入**：国家、ISP
**公式**：

```
WhoisRisk = 25                      # 基础不确定性分
          + (地理风险国家 ? 30 : 0)  # 命中高风险国家 +30
          + (ISP 包含 "hosting" ? 15 : 0)  # 托管类 ISP +15
```

**代码**（`pipeline_components.go`）：

```go
func computeWhoisRiskFromCollected(baseInfo BaseInfoCollectedData) float64 {
    score := 25.0
    if isGeoRiskCountry(baseInfo.Country) {  // RU / KP 等
        score += 30
    }
    if strings.Contains(strings.ToLower(baseInfo.ISP), "hosting") {
        score += 15
    }
    return score
}
```

**为什么是 25 起步？**
- 0 分表示"绝对安全"，但不现实
- 25 分表示"仅凭 IP 归属无法证明安全"的基础不确定性

**举例**：
- 普通美国 IP：25 分
- 俄罗斯 IP：25 + 30 = 55 分
- 俄罗斯 + 云托管 ISP：25 + 30 + 15 = 70 分

### 2. 信誉风险（ReputationScore）

**输入**：本地黑名单 / AbuseIPDB
**公式**：

```
ReputationRisk = 数据源返回的分数
```

**规则**：
- 本地黑名单命中：92 分
- 本地黑名单未命中：20 分
- AbuseIPDB：`abuseConfidenceScore`，白名单压到 20

**举例**：
- 命中本地黑名单：92 分
- 未命中：20 分
- AbuseIPDB 返回 85：85 分

### 3. 攻击面风险（AttackSurfaceRisk）

**输入**：开放端口数、高危端口数、地理风险标记
**公式**：

```
AttackSurfaceRisk = OpenPortCount × 4
                  + HighRiskPortCount × 15
                  + (GeoRiskFlag ? 10 : 0)

如果 > 100，取 100
```

**代码**：

```go
func computeAttackSurfaceRiskFromCollected(attack AttackSurfaceCollectedData) float64 {
    score := float64(attack.OpenPortCount*4 + attack.HighRiskPortCount*15)
    if attack.GeoRiskFlag {
        score += 10
    }
    if score > 100 {
        return 100
    }
    return score
}
```

**权重依据**：
- 普通端口：每个 +4 分（开放越多，暴露面越大）
- 高危端口：每个 +15 分（SSH/SMB/RDP 等，权重更高）
- 地理风险：+10 分（小幅修正，不能压过端口暴露）

**举例**：
- 开放 6 个端口，其中 2 个高危，地理风险 false：
  - `6×4 + 2×15 + 0 = 24 + 30 = 54 分`
- 开放 10 个端口，其中 3 个高危，地理风险 true：
  - `10×4 + 3×15 + 10 = 40 + 45 + 10 = 95 分`

### 4. 行为风险（BehaviorRisk）

**输入**：流量解析结果
**公式**：

```
BehaviorRisk = 4                              # 命中目标流量基础分
             + Σ AnomalyCandidate.Score        # 异常候选加分
             + BurstScore × 0.08               # 突发流量
             + ScanScore × 0.12                # 扫描倾向
             + (DNSEventCount >= 40 ? 3 : 0)   # DNS 事件多
             + (HTTPEventCount >= 20 ? 2 : 0)  # HTTP 事件多
             + (TLSEventCount >= 20 ? 2 : 0)   # TLS 事件多
             + (HighEntropyPacketCount >= 24 ? 4 : 0)  # 高熵载荷
             + (DirectionBias >= 0.92 ? 4 : 0)         # 方向性偏置
             + (UniqueTargetPortCount >= 10 ? 4 : 0)   # 端口密度
             + (TargetPortDensity >= 3 ? 3 : 0)
             + (HighRiskTargetPortCount >= 2 ? 6 : 0)

如果 > 100，取 100
```

**辅助公式**：

```
BurstScore = min(PeakPPS × 2, 100)
ScanScore = min(UniqueTargetPortCount × 2.5 + SynProbeCount × 1.2 + TcpResetCount × 0.2, 100)
```

**异常候选规则**：

| 候选 | 触发条件 | 加分 |
|---|---|---|
| port-scan-candidate | 唯一目标端口数 ≥ 8 且 SYN 探测数 ≥ 8 | 42 |
| dns-spike-candidate | DNS 事件数 ≥ 60 且唯一目标端口数 ≥ 4 | 14 |
| icmp-probe-candidate | ICMP 事件数 ≥ 30 | 20 |
| tcp-reset-burst-candidate | TCP RST 数 ≥ 40 | 8 |

**举例**（在第六章详细讲）。

## 四、第二步：加权融合（四个风险分 → 核心分）

**默认权重**（`config.yaml`）：

```yaml
weights:
  whoisWeight: 0.20
  reputationWeight: 0.35
  attackSurfaceWeight: 0.30
  behaviorWeight: 0.15
```

**公式**：

```
CoreScore = WhoisRisk × 0.20
          + ReputationRisk × 0.35
          + AttackSurfaceRisk × 0.30
          + BehaviorRisk × 0.15
```

**代码**：

```go
func (s WeightedScoreCalculator) Calculate(...) (ScoreResult, error) {
    baseScore := 0.0
    reputationScore := 0.0
    attackSurfaceScore := 0.0
    behaviorScore := 0.0

    for _, factor := range normalized.ScoreFactors {
        switch factor.Key {
        case "whois":
            baseScore += factor.Contribution        // = WhoisRisk × 0.20
        case "reputation":
            reputationScore += factor.Contribution  // = ReputationRisk × 0.35
        case "attack_surface":
            attackSurfaceScore += factor.Contribution
        case "behavior":
            behaviorScore += factor.Contribution
        }
    }

    scoreValue := baseScore + reputationScore + attackSurfaceScore + behaviorScore
    // ...
}
```

**权重为什么这样分配？**

| 维度 | 权重 | 理由 |
|---|---|---|
| 信誉 | 0.35（最高） | 黑名单/AbuseIPDB 直接表达历史滥用证据，解释力最强 |
| 攻击面 | 0.30 | 端口暴露体现当前可达服务和被攻击机会 |
| 基础画像 | 0.20 | 地理、ASN、ISP 能辅助判断，但不应单独决定高风险 |
| 行为 | 0.15（最低） | 流量是增强能力，样本/离线/在线可用性受环境影响 |

**算法版本**：`ahp-entropy-v1`
- `ahp`：层次分析法（Analytic Hierarchy Process）思想，主观定权重
- `entropy`：行为分里有载荷熵指标
- `v1`：第一版

## 五、第三步：规则修正（核心分 → 最终分）

**公式**：

```
RuleAdjustment = 0
GeoRiskFlag               => +6
HighRiskPortCount >= 3    => +5
BehaviorRisk >= 70        => +8
BehaviorRisk <= 10 且 flowMode = disabled => -2

限制在 -5 ~ +15 之间
```

**代码**：

```go
func calculateRuleAdjustmentValue(normalized NormalizedFeatureSet, cfg config.SecurityConfig) float64 {
    adjustment := 0.0
    if normalized.GeoRiskFlag {
        adjustment += 6
    }
    if normalized.HighRiskPortCount >= 3 {
        adjustment += 5
    }
    if normalized.BehaviorRisk >= 70 {
        adjustment += 8
    }
    if normalized.BehaviorRisk <= 10 && normalizeFlowBoundaryMode(normalized.FlowMode) == "disabled" {
        adjustment -= 2
    }
    if adjustment > 15 {
        return 15
    }
    if adjustment < -5 {
        return -5
    }
    return adjustment
}
```

**为什么要规则修正？**

加权模型是线性的，但有些组合特征需要额外表达：
- 地理风险 + 多个高危端口 + 高行为风险 → 组合起来比单独看更危险
- 行为风险很低且流量禁用 → 说明没有动态证据，可以小幅减分

**为什么限制在 -5 ~ +15？**
- 防止规则修正压过加权分数
- 保持评分模型的稳定性

## 六、第四步：最终分和等级映射

**最终分**：

```go
FinalScore = CoreScore + RuleAdjustment
FinalScore 保留两位小数
```

**等级映射**：

```go
func mapRiskLevel(score float64, cfg config.SecurityConfig) string {
    switch {
    case score >= cfg.CriticalRiskThreshold:  // 默认 90
        return "CRITICAL"
    case score >= cfg.HighRiskThreshold:      // 默认 75
        return "HIGH"
    case score >= 45:
        return "MEDIUM"
    default:
        return "LOW"
    }
}
```

**预警触发**：

```go
IsAlertTriggered = FinalScore >= cfg.HighRiskThreshold  // >= 75
```

## 七、完整手算示例（重点！面试必考）

### 示例 1：普通美国 IP

**输入**：
- 国家：US
- ISP：Comcast
- 黑名单：未命中
- 开放端口：2 个（80, 443），无高危
- 地理风险：false
- 流量：禁用（flowMode = disabled）

**第一步：归一化**
- WhoisRisk = 25（基础分）
- ReputationRisk = 20（未命中）
- AttackSurfaceRisk = 2×4 + 0×15 + 0 = 8
- BehaviorRisk = 0（禁用）

**第二步：加权融合**
- CoreScore = 25×0.20 + 20×0.35 + 8×0.30 + 0×0.15
           = 5 + 7 + 2.4 + 0
           = 14.4

**第三步：规则修正**
- GeoRiskFlag = false → 不加分
- HighRiskPortCount = 0 → 不加分
- BehaviorRisk = 0 → 不加分
- BehaviorRisk <= 10 且 flowMode = disabled → -2

- RuleAdjustment = -2

**第四步：最终分**
- FinalScore = 14.4 - 2 = 12.4

**第五步：等级映射**
- 12.4 < 45 → **LOW**

**预警**：不触发

### 示例 2：俄罗斯云主机 IP（命中黑名单）

**输入**：
- 国家：RU
- ISP：Cloud Hosting
- 黑名单：命中
- 开放端口：6 个（22, 80, 443, 445, 3389, 8080），其中 3 个高危（22, 445, 3389）
- 地理风险：true
- 流量：离线 pcap，行为分 60

**第一步：归一化**
- WhoisRisk = 25 + 30 + 15 = 70
- ReputationRisk = 92（命中黑名单）
- AttackSurfaceRisk = 6×4 + 3×15 + 10 = 24 + 45 + 10 = 79
- BehaviorRisk = 60

**第二步：加权融合**
- CoreScore = 70×0.20 + 92×0.35 + 79×0.30 + 60×0.15
           = 14 + 32.2 + 23.7 + 9
           = 78.9

**第三步：规则修正**
- GeoRiskFlag = true → +6
- HighRiskPortCount = 3 → +5
- BehaviorRisk = 60 → 不加分（< 70）

- RuleAdjustment = 11

**第四步：最终分**
- FinalScore = 78.9 + 11 = 89.9

**第五步：等级映射**
- 89.9 >= 75 → **HIGH**

**预警**：触发

### 示例 3：高危 IP（全部拉满）

**输入**：
- 国家：KP（朝鲜）
- ISP：Cloud Hosting
- 黑名单：AbuseIPDB 返回 95
- 开放端口：10 个，其中 4 个高危
- 地理风险：true
- 流量：在线抓包，行为分 85

**第一步：归一化**
- WhoisRisk = 25 + 30 + 15 = 70
- ReputationRisk = 95
- AttackSurfaceRisk = 10×4 + 4×15 + 10 = 40 + 60 + 10 = 110 → **封顶 100**
- BehaviorRisk = 85

**第二步：加权融合**
- CoreScore = 70×0.20 + 95×0.35 + 100×0.30 + 85×0.15
           = 14 + 33.25 + 30 + 12.75
           = 90

**第三步：规则修正**
- GeoRiskFlag = true → +6
- HighRiskPortCount = 4 → +5
- BehaviorRisk = 85 → +8

- RuleAdjustment = 19 → **封顶 +15**

**第四步：最终分**
- FinalScore = 90 + 15 = 105

**第五步：等级映射**
- 105 >= 90 → **CRITICAL**

**预警**：触发


**为什么保存这么多字段？**
- 可解释性：用户能看到每个维度的贡献
- 可追溯性：算法版本和权重配置都记录下来，方便复查
- 审计：知道这条评分是用哪个版本算法算出来的

## 九、评分的可解释性

前端任务详情页会展示：

```
评分因子
├─ 基础属性风险：70.00（权重 0.20，贡献 14.00）
│  └─ 依据：命中地理风险国家 RU (+30)，ISP 为 Cloud Hosting (+15)
├─ 信誉风险：92.00（权重 0.35，贡献 32.20）
│  └─ 依据：命中本地黑名单 local-blacklist.txt
├─ 攻击面风险：79.00（权重 0.30，贡献 23.70）
│  └─ 依据：开放端口 6 个，其中高危端口 3 个 (22, 445, 3389)
├─ 行为风险：60.00（权重 0.15，贡献 9.00）
│  └─ 依据：检测到 DNS 事件 45 次，HTTP 事件 23 次，突发评分 35
└─ 规则修正：+11.00
   └─ 依据：地理风险标记 (+6)，高危端口数 >= 3 (+5)

最终评分：89.90
风险等级：HIGH
```

**为什么可解释性重要？**
- 安全场景：用户需要知道"为什么这个 IP 危险"，才能决定是否封禁
- 面试加分：能讲清楚评分逻辑比"用了机器学习"更有说服力
- 调试方便：评分不对时，能定位是哪个维度出了问题

## 十、本章 Q&A

**Q：为什么信誉权重最高（0.35）？**
A：黑名单和 AbuseIPDB 是基于历史滥用证据的，解释力最强。相比之下：
- 基础画像（地理、ISP）只是辅助判断
- 攻击面（端口）只是暴露面，不代表已被攻击
- 行为（流量）是动态证据，但可用性受环境影响

**Q：为什么行为权重最低（0.15）？**
A：流量采集依赖环境：
- pcap 文件可能没有
- 在线抓包需要 Npcap 和管理员权限
- 样本模式只是演示

如果行为权重太高，没有流量数据时评分会失真。

**Q：规则修正为什么不能直接加到权重里？**
A：权重是线性的（每个维度独立加权），规则修正是非线性的（组合特征）。

例如：
- 地理风险 + 高危端口多 + 行为风险高 → 组合起来比单独看更危险
- 这种"组合爆炸"用权重表达不出来

**Q：评分会不会出现 100 分以上？**
A：会。例如示例 3 的 105 分。但前端展示时可以截断到 100，或者说"105 分表示极度危险"。

**Q：如果用户改了权重，历史任务的评分会变吗？**
A：不会。每条评分记录都保存了当时的权重配置（`weight_profile` 字段），历史评分用历史权重，新任务用新权重。

**Q：如果让我调权重，我会怎么调？**
A：看场景：
- 内网环境：提高行为权重（流量更重要），降低信誉权重（内网 IP 不在黑名单里）
- 公网环境：保持默认
- 高安全场景：提高攻击面权重（端口暴露更严重）

**Q：评分模型有什么局限性？**
A：
1. 权重是主观的，没有数据支撑
2. 规则修正的阈值（如 BehaviorRisk >= 70）是经验值
3. 没有考虑时间因素（一个 IP 去年恶意，今年可能干净了）

改进方向：
- 用历史数据训练权重（逻辑回归、随机森林）
- 加入时间衰减因子
- 加入更多维度（域名信誉、证书透明度日志）
